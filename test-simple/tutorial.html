Local development walkthrough

Test the Fabric network with Docker

This guide continues from the command shown in your terminal: ./network.sh createChannel -c mychannel. It explains the output, verifies the services, deploys the Asset Transfer sample, and runs a client against the channel.

Commands below are run from the fabric-samples/test-network directory unless a step says otherwise. The test network is for learning and local development, not production.

1. Confirm Docker and the Fabric prerequisites

The Docker daemon must be running. The network script also needs the Fabric binaries and configuration installed next to this repository (the bin and config directories), plus the Fabric container images. Check the runtime and current containers: 

docker info
docker compose version
docker ps
cd /path/to/fabric-samples/test-network

Replace /path/to/fabric-samples with the actual location. If the CLI tools or images are missing, follow the Fabric installation guide before continuing. The local Fabric binaries and Docker images should use matching versions.

2. Create mychannel

./network.sh createChannel -c mychannel

This is the command from the provided console output. It does more than create a channel: if it does not find the network services already running, it generates the development identities and starts the peer and orderer containers with Docker Compose first. If they are already up, it reuses them.

The successful run creates the channel artifacts, joins Org1 and Org2 peers, and updates their anchor peers. The sample topology is:

ContainerRoleHost port
orderer.example.comRaft ordering service7050 (and admin 7053)
peer0.org1.example.comOrg1 peer7051
peer0.org2.example.comOrg2 peer9051

These match the example output: the orderer and two peers are listed as running and their ports are published on the host. A successful channel creation does not deploy a smart contract; that is the next step.

About the Podman messages in the example: “Emulate Docker CLI using podman” and the podman-compose provider indicate that this environment routes Docker-compatible commands through Podman. They are informational messages, not Fabric errors. Continue to use the same runtime consistently for status and log commands. If choosing Podman explicitly, the project documents CONTAINER_CLI=podman ./network.sh ....

3. Verify the services and channel

List the running Fabric containers and inspect a peer's startup log:

docker ps --filter label=service=hyperledger-fabric
docker logs --tail 50 peer0.org1.example.com

To verify channel membership from the peer CLI, configure the local tools for Org1. These paths are relative to the test-network directory: 

export PATH="${PWD}/../bin:$PATH"
export FABRIC_CFG_PATH="${PWD}/../config"
export $(./setOrgEnv.sh Org1 | xargs)
peer channel list

The result should include mychannel. The setOrgEnv.sh command sets the peer address, TLS settings, and Org1 administrator identity for this terminal.

4. Deploy the Asset Transfer chaincode

From test-network, deploy the Go implementation in the sample repository: 

./network.sh deployCC \
  -c mychannel \
  -ccn basic \
  -ccp ../asset-transfer-basic/chaincode-go \
  -ccl go

The helper packages the chaincode, installs it on both peers, has both organizations approve its definition, checks the approvals, and commits the definition to mychannel. It requires Go and the jq utility in addition to the Fabric tools. Wait for the command to report successful deployment before running a client.

Other implementations are available in asset-transfer-basic; change the path and language flag to select JavaScript (chaincode-javascript, -ccl javascript), TypeScript (chaincode-typescript, -ccl typescript), or Java (chaincode-java, -ccl java). Install the matching language runtime first.

5. Run the application and exercise the ledger

The Go Gateway client uses the Org1 identity generated for this network and connects to the peer at localhost:7051. From test-network, run: 

cd ../asset-transfer-basic/application-gateway-go
go run .

On its first run, the client submits InitLedger to add the sample assets. It then evaluates GetAllAssets, creates and reads a new asset, transfers it, and demonstrates transaction error handling. The terminal prints the results for each operation. The application initialization is why the deployment command above does not pass a separate chaincode-init option.

The same smart contract supports CreateAsset, ReadAsset, UpdateAsset, TransferAsset, and DeleteAsset. The Asset Transfer README has instructions for running the JavaScript, TypeScript, and Java clients as well.

6. Logs, recovery, and common problems

Inspect logs or current status

docker ps -a
docker logs --tail 100 orderer.example.com
docker logs --tail 100 peer0.org2.example.com

If a command fails

  • “Peer binary and configuration files not found”: install the Fabric binaries and confirm ../bin/peer and ../config exist.
  • Version mismatch warning: use matching Fabric CLI binaries and container image versions.
  • Docker connection error: start the Docker daemon, or confirm the Podman compatibility service used by your environment is available.
  • Channel already exists: do not recreate it; continue to the chaincode deployment step using the existing channel name.
  • Application cannot connect: confirm the two peers are running and their host ports are available, then check the peer logs.

7. Stop the network

cd /path/to/fabric-samples/test-network
./network.sh down
Destructive cleanup: network.sh down removes the network's containers and volumes, including peer ledger data. Use it when you are finished with this local network, not just to close a terminal.
